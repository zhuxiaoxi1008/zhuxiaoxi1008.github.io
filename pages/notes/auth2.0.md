# OAuth 2.0 一周极速学习脑图

---

## 极速版
我们按3小时极速学习大纲中的核心概念，逐一解释。每个概念用最简洁的语言说明，不展开细节。

### 1. OAuth 2.0 是什么
定义：一种授权协议，允许第三方应用在用户授权下，访问用户在其他服务上的数据，而无需获取用户的密码。

本质：委托授权（用户把权限委托给第三方应用）。

不是：身份认证协议（它不关心用户是谁，只关心用户是否同意授权）。

### 2. 解决的问题
传统方式：第三方应用直接拿用户的用户名和密码去访问资源服务 → 风险高（密码泄露、权限过大、无法撤销）。

OAuth 2.0：通过颁发临时、可撤销、限定权限的令牌（Token），替代密码，减少攻击面。

### 3. 四种角色
角色 | 说明 | 例子（小兔打单软件）
--- | --- | ---
资源拥有者（Resource Owner） | 用户，拥有数据 | 小明
第三方软件（Client） | 请求访问的应用 | 小兔打单软件
授权服务（Authorization Server） | 负责用户授权、颁发令牌 | 京东商家开放平台的授权服务
受保护资源服务（Resource Server） | 存储用户数据，接受令牌访问 | 京东订单API

### 4. 授权码许可流程（最核心）
目的：安全地获取访问令牌。

步骤（简化版）：
1. 第三方软件重定向用户到授权服务（带上 client_id 和重定向地址）。
2. 用户登录并同意授权。
3. 授权服务返回授权码（code）到第三方软件的重定向地址（前端）。
4. 第三方软件后端用授权码 + client_secret 换取访问令牌（后端通信）。
5. 第三方软件用访问令牌调用受保护资源。

为什么需要授权码？
- 如果直接返回令牌，令牌会暴露在浏览器（不安全）。
- 通过授权码 + 后端换取，令牌只在服务器之间传输，更安全。

两次重定向：
- 第一次：用户从第三方软件跳转到授权服务。
- 第二次：授权服务返回授权码，用户跳回第三方软件。

### 5. 四种授权许可类型
类型 | 场景 | 安全性
--- | --- | ---
授权码许可（Authorization Code） | 有后端的Web应用 | 最高（推荐）
资源拥有者凭据许可（Password） | 第一方官方应用 | 中（需用户提供密码）
客户端凭据许可（Client Credentials） | 无用户参与的后端服务调用 | 中（仅用 client_id/secret）
隐式许可（Implicit） | 无后端的单页应用（已废弃） | 低（令牌暴露在浏览器）

### 6. 令牌（Token）
访问令牌（Access Token）：
- 用于访问受保护资源
- 短生命周期（通常1小时）
- 不透明（第三方无需解析内容）

刷新令牌（Refresh Token）：
- 用于获取新的访问令牌
- 长生命周期（通常数天或数周）
- 一次性使用（使用后通常颁发新刷新令牌）

### 7. JWT（JSON Web Token）
是什么：
- 一种结构化令牌格式，包含三部分：Header.Payload.Signature。

Header：
- 算法和类型

Payload：
- 数据（如用户ID、过期时间）

Signature：
- 签名，防篡改

优点：
- 自包含（无需查数据库）
- 可签名
- 适合内部微服务传递用户信息

缺点：
- 不能主动失效（在有效期内永远有效）
- 信息可被解密（不存敏感数据）

### 8. 安全与常见漏洞
漏洞 | 描述 | 防御
--- | --- | ---
CSRF | 攻击者诱导用户点击恶意链接，使用用户的已授权状态发起请求 | 使用 state 参数，验证请求来源
XSS | 注入恶意脚本，窃取令牌或用户信息 | 输入过滤转义
水平越权 | 用户A访问用户B的数据 | 服务端校验数据归属（如订单ID属于当前用户）
授权码失窃 | 攻击者截获授权码，换取令牌 | 授权码一次性使用 + 绑定 client_id
重定向URI篡改 | 攻击者伪造回调地址，拦截授权码 | 精确匹配注册的回调地址

### 9. PKCE（Proof Key for Code Exchange）
出现原因：
- 移动App无法安全保存 client_secret，但仍需使用授权码流程。

原理：
1. App 生成一个随机字符串 code_verifier
2. 对 code_verifier 哈希得到 code_challenge
3. 授权请求时带上 code_challenge
4. 换取令牌时带上 code_verifier
5. 授权服务验证 code_verifier 与 code_challenge 匹配

效果：
- 即使授权码被拦截，攻击者没有 code_verifier 也无法换取令牌

### 10. OIDC（OpenID Connect）
是什么：
- 基于 OAuth 2.0 的身份认证协议。

解决了什么：
- OAuth 2.0 只授权，不告诉第三方"用户是谁"。
- OIDC 增加了ID令牌，用于证明用户身份。

ID令牌：
- JWT格式，包含用户唯一标识（sub）、颁发者、过期时间等。

UserInfo端点：
- 通过访问令牌可获取更详细的用户信息（如昵称、头像）。

### 11. 微服务中的混合模式
外部：
- 使用 OAuth 2.0 访问令牌（不透明，隐藏用户信息）。

网关层：
- 校验令牌，转换为 JWT（包含用户信息）。

内部微服务：
- 传递 JWT，无需再查询授权服务。

好处：
- 外部安全，内部高效。

### 12. 开放平台对接实战关键点
注册应用：
- 获得 client_id 和 client_secret
- 配置回调地址 redirect_uri

请求授权码：
```
/authorize?response_type=code&client_id=xxx&redirect_uri=xxx&scope=xxx&state=xxx
```

换取令牌：
```
/token?grant_type=authorization_code&code=xxx&client_id=xxx&client_secret=xxx&redirect_uri=xxx
```

使用令牌：
- 在请求头添加 `Authorization: Bearer <access_token>`

以上是 OAuth 2.0 极速版核心概念的逐一解答。每个概念都只保留了最必要的定义和关键词，适合快速记忆和面试突击。如果需要更详细的某个概念，可以单独提问。

## 知识图谱

### OAuth 2.0 知识脑图

#### 1. 核心概念
- 是什么
  - 授权协议（不是身份认证）
  - 委托授权：用令牌代替密码
- 解决了什么
  - 第三方软件无需存储用户密码
  - 减少攻击面
- 四种角色
  - 资源拥有者（用户）
  - 第三方软件（客户端）
  - 授权服务
  - 受保护资源服务

#### 2. 授权码许可流程（最常用、最安全）
- 为什么需要授权码
  - 避免令牌暴露在浏览器
  - 通过两次重定向建立前后端连接
- 步骤
  1. 第三方软件引导用户到授权服务
     - 参数：response_type=code, client_id, redirect_uri, scope, state
  2. 用户登录并授权
  3. 授权服务返回授权码（code）到重定向URI
  4. 第三方软件后端用code + client_secret换令牌
  5. 授权服务返回 access_token（可选 refresh_token）
  6. 第三方软件用 access_token 调用受保护资源
- 通信方式
  - 前端通信：获取授权码（间接）
  - 后端通信：换取令牌（直接）

#### 3. 令牌
- 访问令牌（access_token）
  - 用于调用受保护资源
  - 短有效期
  - 不透明（第三方无需解析）
- 刷新令牌（refresh_token）
  - 用于获取新访问令牌
  - 长有效期，一次性使用
  - 颁发新令牌时可同时更新刷新令牌
- 结构化令牌：JWT
  - 三部分：Header, Payload, Signature
  - 优点：自包含、无需存储、可签名
  - 缺点：无法主动失效、信息可解密
  - 使用场景：内部微服务传递用户信息

#### 4. 四种授权许可类型
- 授权码许可（Authorization Code）
  - 最安全，有后端服务器时使用
- 资源拥有者凭据许可（Password）
  - 第一方应用，用户直接提供账号密码
- 客户端凭据许可（Client Credentials）
  - 无用户参与，适用于后端服务调用
- 隐式许可（Implicit）
  - 已废弃，不安全，仅用于无后端单页应用

#### 5. 安全与常见漏洞
- HTTPS 必须
- CSRF
  - 防御：使用 state 参数
- XSS
  - 防御：输入过滤转义
- 水平越权
  - 防御：校验数据归属（如订单ID属于当前用户）
- 授权码失窃
  - 防御：授权码一次性 + 校验 app_id
- 重定向URI篡改
  - 防御：精确匹配回调地址
- 移动App特别风险
  - 无法安全保存 client_secret
  - 解决方案：PKCE（Proof Key for Code Exchange）
    - code_verifier + code_challenge
    - 防止授权码被拦截后换取令牌

#### 6. 扩展：OIDC（身份认证）
- OIDC 基于 OAuth 2.0 构建
- 新增 ID 令牌（JWT格式）
  - 包含用户标识（sub）、颁发者、受众、过期时间
- UserInfo 端点
  - 用访问令牌获取用户详细信息
- 单点登录（SSO）
  - 多个应用共享同一身份认证服务

#### 7. 微服务架构中的集成（混合模式）
- 外部使用 OAuth 2.0 令牌（不透明）
- 网关层校验令牌并转换为 JWT
- 内部微服务使用 JWT 传递用户信息
- 优势
  - 外部隐藏用户信息
  - 内部免去频繁查询授权服务

#### 8. 开放平台实战
- 第三方软件接入流程
  - 注册应用（app_id, app_secret, redirect_uri）
  - 引导授权（获取 code）
  - 换取令牌
  - 调用 API
- 关键参数
  - response_type=code
  - client_id, redirect_uri, scope, state
- 各大平台
  - 微信、支付宝、京东、美团
  - 均推荐授权码流程

#### 9. 常见问题
- OAuth 2.0 是授权协议，不是身份认证协议
- 刷新令牌不能使访问令牌一直有效（刷新令牌也有有效期）
- JWT 即使使用 HTTPS，仍需加密以防信息泄露
- ID 令牌和访问令牌分工不同，不相互替换
- PKCE 用于原生移动端防护
